# Report workflow: architecture

UML for both shapes of the toy, plus the state machine itself. In the classic shape that
machine lives in the overridden methods of four classes. In the modern shape it is a
seven-row table, and the diagram below was printed from that table.

## The machine

Generated by `uv run modern.py --diagram` from `TRANSITIONS`. Any event not shown from a
status is rejected.

```mermaid
stateDiagram-v2
    [*] --> draft
    draft --> draft : edit
    draft --> preliminary : sign_preliminary
    draft --> final : sign_final
    preliminary --> preliminary : edit
    preliminary --> final : sign_final
    final --> appended : addend
    appended --> appended : addend
```

## Participants

| Pattern | GoF participant | `classic.py` | `modern.py` |
|---|---|---|---|
| State | Context | `Report`: holds `state`, delegates each event to it | `Report`, a frozen record with a `status` field; `fire()` does the delegating |
| | State | `ReportState`: every event raises by default | `Status` (`StrEnum`) |
| | ConcreteState | `Draft`, `Preliminary`, `Final`, `Appended` | the four `Status` members |
| | state-specific behaviour | the methods each subclass overrides | the rows of `TRANSITIONS` for that status |
| | transition | a state assigns `report.state = Next()` | `TRANSITIONS[(status, event)]` |
| Observer | Subject | `Report` (`_listeners`, `_handle()`) | `fire()` (its `hooks=` argument) |
| | Observer | `ReportListener` (ABC) | `Hook`, a `Callable` type alias |
| | ConcreteObserver | `AuditLog`, `ReferrerNotifier` | `audit(out)`, `notify_referrer(out)` closures |

## Classic: the machine spread across classes

```mermaid
classDiagram
    direction LR

    namespace StatePattern {
        class Report {
            +state: ReportState
            +body: str
            +addenda: list~str~
            +status: str
            +edit(text) None
            +sign_preliminary() None
            +sign_final() None
            +addend(text) None
            -_handle(event, action) None
        }
        class ReportState {
            <<abstract>>
            +name: str
            +edit(report, text) None
            +sign_preliminary(report) None
            +sign_final(report) None
            +addend(report, text) None
        }
        class Draft {
            +edit()
            +sign_preliminary()
            +sign_final()
        }
        class Preliminary {
            +edit()
            +sign_final()
        }
        class Final {
            +addend()
        }
        class Appended {
            +addend()
        }
    }

    namespace ObserverPattern {
        class ReportListener {
            <<abstract>>
            +on_event(event, before, after) None*
        }
        class AuditLog {
            +on_event(event, before, after) None
        }
        class ReferrerNotifier {
            +on_event(event, before, after) None
        }
    }

    ReportState <|-- Draft
    ReportState <|-- Preliminary
    ReportState <|-- Final
    ReportState <|-- Appended
    Report o-- ReportState : current state
    ReportState ..> Report : sets report.state
    ReportListener <|-- AuditLog
    ReportListener <|-- ReferrerNotifier
    Report o-- "*" ReportListener : notifies
```

**State vs Strategy.** Put this diagram next to
[training-loop's](../training-loop/ARCHITECTURE.md) `Trainer o-- LRSchedule`. The context
holds an interface with several implementations in both. One arrow differs:
`ReportState ..> Report : sets report.state`. A strategy never replaces itself, but a state
does.

## Modern: the machine as a table

```mermaid
classDiagram
    direction LR

    class Status {
        <<StrEnum>>
        DRAFT
        PRELIMINARY
        FINAL
        APPENDED
    }
    class Event {
        <<StrEnum>>
        EDIT
        SIGN_PRELIMINARY
        SIGN_FINAL
        ADDEND
    }
    class TRANSITIONS {
        <<dict>>
        +key: tuple~Status, Event~
        +value: Status
    }
    class Report {
        <<frozen dataclass>>
        +status: Status
        +body: str
        +addenda: tuple~str~
    }
    class Hook {
        <<type alias>>
        +__call__(event, before: Report, after: Report) None
    }
    class fire {
        <<function>>
        +fire(report, event, text, *, hooks) Report
    }
    class to_mermaid {
        <<function>>
        +to_mermaid() str
    }
    class audit {
        <<function>>
        +audit(out) Hook
    }
    class notify_referrer {
        <<function>>
        +notify_referrer(out) Hook
    }

    TRANSITIONS ..> Status
    TRANSITIONS ..> Event
    Report ..> Status
    fire ..> TRANSITIONS : looks up
    fire ..> Report : returns a new one
    fire ..> Hook : calls each
    to_mermaid ..> TRANSITIONS : renders
    audit ..> Hook : returns
    notify_referrer ..> Hook : returns
```

Two functions read `TRANSITIONS`: `fire()` *runs* the machine and `to_mermaid()` *draws* it.
That second reader is what you gain by turning the machine into data.

## Runtime: one event, both shapes

```mermaid
sequenceDiagram
    participant R as run()
    participant C as Report (classic)
    participant S as Preliminary state
    participant F as fire() (modern)
    participant T as TRANSITIONS
    participant L as listeners / hooks

    R->>C: sign_final()
    C->>S: sign_final(report)
    S->>C: report.state = Final()
    C->>L: on_event(sign_final, preliminary, final)

    R->>F: fire(report, SIGN_FINAL)
    F->>T: (PRELIMINARY, SIGN_FINAL)?
    T-->>F: FINAL
    F->>L: hook(SIGN_FINAL, before, after)
    F-->>R: new Report(status=FINAL)
```
